# Fruta — Behavioral Feature Inventory

Source: Apple "Fruta: Building a Feature-Rich App with SwiftUI" sample (WWDC20/21 sample code), read directly from source under `Shared/`, `iOS/`, `macOS/`, `Widgets/`. 56 Swift files, ~4,500 lines. This document describes **behavior**, not implementation code, for a clean-room reimplementation.

Targets in the Xcode project: **Fruta iOS** (simple, no widgets/App Clip), **Fruta iOS All** (adds Widgets extension + embeds App Clip), **Fruta macOS** (simple), **Fruta macOS All** (adds Widgets extension), **Fruta iOS Widgets**, **Fruta macOS Widgets**, **Fruta iOS Clip** (the App Clip). Three Active-Compilation-Condition flags gate shared code per target: `DEBUG`, `EXTENDED_ALL` (present on every "All" and Clip build, i.e. "has widgets/App-Clip-adjacent code compiled in"), and `APPCLIP` (only the Clip target).

---

## 1. App structure & navigation

### Entry points (three separate `@main` types, one shared view tree)
- **`FrutaApp`** (`Shared/FrutaApp.swift`) — the iOS/macOS app. Creates one `Model` as `@StateObject`, injects it as `.environmentObject`, wraps `ContentView()` in a single `WindowGroup`. Registers menu-bar commands via `.commands { SidebarCommands(); SmoothieCommands(model: model) }` — `SidebarCommands()` is the stock SwiftUI command group that adds the "Show/Hide Sidebar" menu item on macOS; `SmoothieCommands` adds a custom "Smoothie" menu with a "Favorite" toggle bound to ⌥⌘+.
- **`FrutaAppClip`** (`iOS/FrutaAppClip.swift`) — the App Clip's own entry point. Its scene is just `NavigationView { SmoothieMenu() }` (no sidebar/tab chrome at all — the Clip always shows the flat smoothie list). Handles `onContinueUserActivity(NSUserActivityTypeBrowsingWeb:)` to parse the invocation URL.
- **`FrutaWidgets`** (`Widgets/FrutaWidgets.swift`) — a `WidgetBundle` exposing two widgets (`FeaturedSmoothieWidget`, `RewardsCardWidget`).

All three share `Model`, all Smoothie/Ingredient/Nutrition/Recipe/Order/Rewards views, and all button/animation styles.

### Root navigation switch — `ContentView`
`ContentView` is the single router for the full app (not the Clip, which bypasses it):
- **macOS**: always `AppSidebarNavigation()`.
- **iOS**: reads `@Environment(\.horizontalSizeClass)`. `.compact` (iPhone, iPad narrow split) → `AppTabNavigation()`. Regular width (iPad wide, most iPad orientations) → `AppSidebarNavigation()`.
- This means the **same iPad can flip between tab bar and sidebar live** as the app window/split-view is resized — SwiftUI re-evaluates `horizontalSizeClass` and swaps the whole navigation shell.

### Sidebar navigation — `AppSidebarNavigation` (regular width iOS + all of macOS)
- `NavigationView` in the classic 2-or-3-column sidebar style (this predates `NavigationSplitView`; uses `NavigationLink(tag:selection:)` bound to an enum `NavigationItem { menu, favorites, recipes }`).
- Sidebar `List` rows: **Menu** (`list.bullet` icon) → `SmoothieMenu()`; **Favorites** (`heart` icon) → `FavoriteSmoothies()`; **Recipes** (`book.closed` icon) → `RecipeList()`, but the Recipes row only compiles in under `EXTENDED_ALL` (so the "simple" targets have no Recipes section in the sidebar at all).
- Sidebar has `.navigationTitle("Fruta")` and, under `EXTENDED_ALL`, a `.safeAreaInset(edge: .bottom)` **"Pocket"** — a capsule-styled Rewards button pinned under the sidebar list.
- Two placeholder detail panes are declared side-by-side (a 2nd and 3rd `NavigationView` column): "Select a category" and "Select a smoothie", each centered secondary-colored text filling the pane, background/ignoresSafeArea — the classic "nothing selected yet" empty state for multi-column navigation. The innermost pane also carries a disabled `SmoothieFavoriteButton` in its toolbar as a placeholder.
- **Pocket** (nested type): a `Button` styled `.capsule`, `.controlSize(.large)`, labeled "Rewards" / `seal` icon, that presents `RewardsView()` in a `.sheet`. On iOS the sheet gets a top-trailing overlay "Done" button (bold, `.capsule` style, bound to `.keyboardShortcut(.defaultAction)` i.e. Return/Enter); on macOS the sheet is framed `400–600 × 400–600` with a `.confirmationAction` toolbar "Done" button instead (native sheet chrome).

### Tab navigation — `AppTabNavigation` (compact-width iOS only)
- `TabView` with 2 tabs in the base build, 4 under `EXTENDED_ALL`:
  1. **Menu** (`list.bullet`) → `NavigationView { SmoothieMenu() }`
  2. **Favorites** (`heart.fill`) → `NavigationView { FavoriteSmoothies() }`
  3. *(EXTENDED_ALL only)* **Rewards** (`seal.fill`) → `NavigationView { RewardsView() }`
  4. *(EXTENDED_ALL only)* **Recipes** (`book.closed.fill`) → `NavigationView { RecipeList() }`
- So the "simple" (non-EXTENDED_ALL) iOS build in compact width has **only Menu + Favorites** tabs — no Rewards or Recipes surface reachable at all, and correspondingly no Sign in with Apple / rewards UI compiles into that target.
- Each tab label uses `Label { Text(...) } icon: { Image(systemName:) }` with an explicit `.accessibility(label:)` mirroring the text — a defensive accessibility pattern repeated through the codebase (custom icon+text compositions get an explicit accessibility label rather than relying on system inference).

### Navigation-list pattern shared by Menu/Favorites/Recipes
All three sections funnel through **`SmoothieList`** (see §2) which renders a `List` of `SmoothieRow`s behind `NavigationLink(tag: smoothie.id, selection: $model.selectedSmoothieID)`. Selection state (`Model.selectedSmoothieID`) is **shared app-wide on the model**, not scoped per list — this is what lets the App Clip's URL-driven deep link (`smoothieID` query param) and the widget/App-Clip flows push the same detail screen from outside the list itself.

## 2. Screen-by-screen behavior

### 2.1 Smoothie Menu / Favorites / Recipes list — `SmoothieList` + `SmoothieRow`
- **`SmoothieMenu`**: thin wrapper — `SmoothieList(smoothies: Smoothie.all())` with nav title "Menu". Always includes paid/recipe-locked smoothies (`includingPaid` defaults to `true`) — **the IAP gate only locks the printable recipe, never ordering the smoothie itself.**
- **`FavoriteSmoothies`**: `SmoothieList(smoothies: favoriteSmoothieIDs.map{...})`, nav title "Favorites". **Empty state**: an `.overlay` shows "Add some smoothies to your favorites!" (secondary color, centered, full-bleed background) whenever `favoriteSmoothieIDs.isEmpty`.
- **`RecipeList`** (EXTENDED_ALL only, see §2.5): same `SmoothieList`-adjacent row (`SmoothieRow`) but pushes to `RecipeView` instead of `SmoothieView`, and its underlying smoothie set is filtered by `model.allRecipesUnlocked` (locked smoothies simply aren't in the array — no per-row "locked" badge/disabled state, they're just absent until purchase).
- **`SmoothieList` behavior** (shared engine):
  - Filters the passed-in smoothie array by `smoothie.matches(model.searchString)` (title OR any non-water ingredient name, case-insensitive) and sorts by localized title compare.
  - **Search**: `.searchable(text: $model.searchString)` with a suggestions closure — `ForEach(model.searchSuggestions)` renders `Text(name).searchCompletion(name)`. `model.searchSuggestions` = all `Ingredient`s whose name case-insensitive-contains the current search string but isn't an exact case-insensitive match (so once you've typed the full ingredient name, it stops suggesting itself). Search state (`model.searchString`) lives on the shared model, so switching tabs mid-search does not reset it.
  - **Swipe action**: leading/trailing swipe reveals a "Favorite" button (heart icon, tinted `.accentColor`) that calls `model.toggleFavorite(smoothieID:)` inside `withAnimation`.
  - **Selection sync**: wraps the `List` in `ScrollViewReader`; each row's `NavigationLink` has `.onChange(of: model.selectedSmoothieID)` that, when the selection changes externally (e.g. from a deep link), verifies the smoothie still exists, calls `proxy.scrollTo(smoothie.id)` to bring the row into view, then re-confirms the selection — this is how App-Clip/widget-driven navigation scrolls the list to the right row before pushing detail.
  - **Accessibility Rotor**: two custom rotors are registered — "Smoothies" (all rows) and "Favorite Smoothies" (rows where `model.isFavorite`) — letting VoiceOver users jump directly between favorites without swiping through the whole list.
- **`SmoothieRow`**: 60×60 rounded-corner (10pt iOS / 4pt macOS) smoothie thumbnail with a 0.5pt quaternary stroke overlay, title (`.headline`), a localized ingredient list line (`ListFormatter.localizedString(byJoining:)` — produces natural "A, B, and C" lists per-locale) capped to 2 lines, and calorie text (`smoothie.energy.formatted(.measurement(width: .wide, usage: .food))`, secondary color, 1 line). The whole row collapses to one accessibility element combining all children, with the ingredient Text carrying its own explicit `.accessibility(label:)` spelling out "Ingredients: …" so VoiceOver doesn't just read the truncated 2-line string.

### 2.2 Smoothie detail — `SmoothieView`
The centerpiece screen; heaviest use of transitions in the app.
- **Header** (`SmoothieHeaderView`, shared with recipe-adjacent screens): adapts to size class.
  - *Compact/iOS-narrow* ("full-bleed"): full-width smoothie image (`aspectRatio(.fill)`) stacked above a leading-aligned VStack with description text + calorie line (secondary, subheadline).
  - *Wide* (iPad regular / macOS): a 250pt-tall horizontal card — left side is title (macOS only, large-title-bold) + description (title2) + calorie line pinned to the bottom; right side is a 220×250 clipped image — the whole card clipped to a 20pt continuous rounded rect with a 0.5pt quaternary stroke border, padded on all sides.
  - Entire header collapses into one combined accessibility element; the image itself is `.accessibility(hidden: true)` (decorative, since the description conveys the same info).
- **Description text** uses `AttributedString` decoded from localized markdown (`*emphasis*` in the source strings), so bold spans render natively from the localized string itself — no manual attributed-string construction per locale.
- **Ingredient grid**: a `LazyVGrid` of adaptive columns (min 130pt) under a section header "Ingredients" (from a dedicated `Ingredients` string table, chosen specifically because "ingredient" translates differently by semantic context in some languages — comment explicitly calls this out). Each cell is a tappable `IngredientGraphic` in `.thumbnail` style.
- **Ingredient card hero transition** (the app's signature SwiftUI moment):
  - Tapping a thumbnail sets `selectedIngredientID` inside `withAnimation(.openCard)` (spring, response 0.45, damping 0.9) and sets `topmostIngredientID` immediately (unanimated) so the tapped card z-fights correctly during the transition.
  - A `matchedGeometryEffect` (single shared `@Namespace`) links each grid thumbnail (`isSource: !presenting`) to a full-size `IngredientCard` overlay rendered in a `ForEach` over all ingredients sitting above the scroll content (`isSource: presenting` on the overlay copy) — so the thumbnail visually flies/morphs into a large card in place, not a modal push.
  - While a card is open: a full-screen `.regularMaterial` scrim fades in behind it; the scrolling content behind is marked `.accessibility(hidden: true)`; the opened card gets `shadow`, full opacity, elevated `zIndex`, `.accessibility(sortPriority: 1)` and un-hidden — every other (invisible) overlay card stays `opacity(0)`/`hidden` in the tree so VoiceOver can't land on them.
  - Closing reverses with `.closeCard` (spring, response 0.35, damping 1) — asymmetric timing from opening, deliberately.
  - **The card itself flips** (`IngredientCard` → `FlipView`, custom `AnimatableModifier`-based 3D Y-axis `rotation3DEffect`, spring `.flipCard` response 0.35/damping 0.7): front face is the big ingredient photo + title (title font size itself is **animatable** via a custom `AnimatableFontModifier`, so font size actually tweens continuously during open/close rather than snapping) with a "Close" and "Open Nutrition Facts" round icon button (`CardActionButton`, squishable style, no fade-on-press). Tapping "Open Nutrition Facts" flips to the back face: `NutritionFactView` (see §4) over a `.thinMaterial` backdrop with a "Close Nutrition Facts" button that flips back.
  - Every ingredient in the code carries a hand-authored `CardTitle` (color, rotation angle, pixel offset, `BlendMode`, opacity, font size) and separate `Crop` (x/y offset + scale) structs for **thumbnail vs. card presentation** — i.e. the same source photo is cropped/zoomed differently, and its title label positioned/rotated/blended differently, depending on whether it's shown small or large. This per-ingredient art-direction table is entirely data, not per-view logic.
- **Bottom action bar** (`.safeAreaInset(edge: .bottom)`, divider + `.bar` background): conditionally shows **`RedeemSmoothieButton`** ("Redeem Free Smoothie!", filled accent-color capsule) if `model.account?.canRedeemFreeSmoothie == true`, else **`PaymentButton`** (Apple-Pay-styled buy button, see §3). This is the only place the free-smoothie redemption path is reachable.
- **Favorite toggle**: `SmoothieFavoriteButton` lives in the navigation-bar `.toolbar`, not on the card — heart/heart.fill Label, disabled if no smoothie is selected (defensive, since this same button is reused as a *disabled* toolbar placeholder in the sidebar's empty detail pane).
- **Order confirmation**: successful order or redeem sets `presentingOrderPlacedSheet = true`, presenting `OrderPlacedView` (§2.3) as a `.sheet`.
- **Payments-disabled alert**: if `model.isApplePayEnabled == false` (only ever flipped by the App Clip's location-verification callback — see §6), tapping the buy button shows an `Alert` — "Payments Disabled" / "The Fruta QR code was scanned too far from the shop, payments are disabled for your protection." — and the order never happens.
- macOS gets an explicit `.frame(minWidth: 500, idealWidth: 700, ...)` window sizing; content is also capped to a 600pt reading width and re-expanded to fill on macOS.

### 2.3 Order placed / pickup status — `OrderPlacedView`
- Full-bleed background: the ordered smoothie's photo (`aspectRatio(.fill)`) if there is an order, else a flat `order-placed-background` color; while the order isn't yet ready, an `.ultraThinMaterial` veil sits over the photo.
- Centerpiece is a **flippable circular card** (`FlipView`, same `.flipCard` spring used by ingredient cards): front = "Thank you for your order! / We will notify you when your order is ready."; back = "Your smoothie is ready! / {name} is ready to be picked up." Card is a 300×300 circle with centered, uppercase-title + rounded-design subtitle text.
- **Auto-ready timer**: on `.onAppear`, schedules `model.orderReadyForPickup()` after a **hard-coded 4 second delay** via `DispatchQueue.main.asyncAfter` — there's no real backend, this is a simulated "your order is ready" beat. `order.isReady` flip is animated with a spring (response 0.25, damping 1).
- **EXTENDED_ALL-only bottom banner**: shown whenever `!model.hasAccount` (or, on the App Clip, whenever the App-Store overlay is up) — "Sign up to get rewards!" + a `SignInWithAppleButton(.signUp, ...)` bound to `model.authorizeUser`. Once `model.hasAccount` flips true, the banner animates out (same spring).
- **App-Clip-only**: an `SKOverlay.AppClipConfiguration(position: .bottom)` App Store overlay is triggered (`presentingAppStoreOverlay`) either immediately on appear (if already "has account") or reactively via `.onChange(of: model.hasAccount)` — i.e. once a Clip user signs in with Apple, the Clip immediately prompts them to get the full app.

### 2.4 Rewards — `RewardsView` + `RewardsCard` (EXTENDED_ALL only)
- `RewardsView` centers a `RewardsCard` over a `BubbleBackground` (animated ambient bubbles, §7), with `.navigationBarTitleDisplayMode(.inline)` on iOS.
- `RewardsCard`: a rounded card headed "Rewards Card", containing a 5-column `LazyVGrid` of 10 **stamp slots**. Each slot's state is derived from `totalStamps` (= `account.unspentPoints`) vs. index: unstamped (empty translucent circle), already-stamped (static filled seal), or *newly*-stamped-this-visit (animated). Non-iOS(macOS excluded)/non-macOS platforms animate each new stamp popping in (`seal.fill`, scale 2→1 + opacity 0→1) with a per-slot staggered spring delay (`0.15s * (index+1)`) — on macOS the pop is applied instantly, no animation. Below the card (non-compact mode only): "You are N points away from a free smoothie!" (pluralized via `.stringsdict`, see §5) if signed in, or (EXTENDED_ALL) "Sign up to get rewards!" if not.
- Whole card is dimmed to 50% opacity if `!hasAccount`.
- A `compact` flag (used by the widget, §6) shrinks spacing/typography and hides the caption line — same view, two densities.
- **`RewardsView` clears "unstamped" state on disappear** (`model.clearUnstampedPoints()`) — so the "just earned" stamp-pop animation only plays once per visit; leaving and returning to Rewards after a fresh order won't re-play the pop for stamps you've already seen animate.
- **EXTENDED_ALL bottom bar**: divider +, if `!hasAccount`, a `SignInWithAppleButton(.signUp, ...)` over a `.bar` material — the second of two Sign-in-with-Apple entry points in the app (the other is in `OrderPlacedView`'s banner).

### 2.5 Recipes — `RecipeList` + `RecipeView` + `RecipeUnlockButton` (EXTENDED_ALL only)
- **`RecipeList`**: same row styling as the menu, but the underlying data set is `Smoothie.all(includingPaid: model.allRecipesUnlocked)` — i.e. **locked recipes are entirely absent from the list**, not shown-but-disabled. List animates (spring 1s/damping 1) whenever `allRecipesUnlocked` flips, so unlocking causes the newly-revealed rows to animate into place.
  - **Unlock call-to-action** (`RecipeUnlockButton`), shown only while `!allRecipesUnlocked`: on iOS it's an inline `List` section (row insets zeroed, separators hidden) above the recipe rows; on macOS it's pinned via `.safeAreaInset(edge: .bottom)`. It transitions in/out with `.scale.combined(with: .opacity)`.
  - `RecipeUnlockButton` itself: a background photo (`smoothie/recipes-background`, 225pt iOS / 150pt macOS) with a bottom bar over `.regularMaterial` showing the product's live StoreKit `displayName`/`description`, and — once `product.availability` resolves to `.available(displayPrice:)` — a purchase button styled `.purchase` (`PurchaseButtonStyle`: high-contrast black/white pill, color-scheme-aware) showing the localized price. While the product hasn't loaded yet, the button shows a synthesized "Unlock All Recipes / Loading…" placeholder with `.unavailable` availability (no buy button rendered at all).
- **`RecipeView`** (a smoothie's actual recipe, distinct from `SmoothieView`'s order screen): full-width rounded-corner (24pt) photo with an overlay **`StepperView`** (see below) reading "N Smoothies" batch multiplier, then an "Ingredients" section listing every `MeasuredIngredient` scaled by the current batch count, each row a large tappable **checklist item**: ingredient thumbnail, name, a `MeasurementView` (unit icon + localized quantity string, e.g. "1.5 cups"), and a trailing circular checkbox toggle (`CircleToggleStyle`, checkmark.circle.fill / plain circle) the user can tap to mark that ingredient gathered — **this checked state is purely local `@State`, not persisted**, resets whenever the view is recreated.
- **`StepperView`**: a capsule (thin-material background) with a decrement/increment `CountButton` on each side and a centered label; increments/decrements clamp to `[minValue, maxValue]` = `[1, 9]` here. Tapping tilts the whole capsule in 3D (`rotation3DEffect`, ±3° Y-axis) briefly toward the direction of change, then springs back — a physical "nudge" affordance. Exposes an `.accessibilityRepresentation` that substitutes a native `Stepper` (so VoiceOver users get standard increment/decrement rotor gestures instead of having to find the tiny +/- buttons).
- Recipe screen keeps the same favorite-toggle toolbar button as the order screen.

### 2.6 Settings / account
There is **no dedicated Settings screen**. Account state is implicit: "having an account" (`model.hasAccount`) is established purely by completing Sign in with Apple from one of the two inline prompts (Order-Placed banner, Rewards bottom bar); there is no profile/sign-out/preferences UI anywhere in the app. In the iOS Simulator, `Model.hasAccount` is hard-forced to `true` (`#if targetEnvironment(simulator)`) so the signed-out banners never appear on Simulator, only on device.

## 3. Core loop

1. **Browse** — Menu/Favorites/Recipes lists, filtered/searched, matched-geometry into a smoothie's detail (`SmoothieView`) or recipe (`RecipeView`).
2. **Inspect ingredients** — tap any ingredient thumbnail on `SmoothieView` to hero-transition into a full card; flip the card to read per-ingredient nutrition facts (§4) scaled to that smoothie's actual measured quantity.
3. **Order**:
   - Full price → `PaymentButton` (Apple-Pay-look button, see §6) → `model.orderSmoothie(smoothie)`.
   - If eligible (`account.canRedeemFreeSmoothie`, i.e. `unspentPoints >= 10`) → `RedeemSmoothieButton` instead → `model.redeemSmoothie(smoothie)`, which debits `pointsSpent += 10` then calls the same `orderSmoothie`.
   - Either path sets `model.order = Order(smoothie:, points: 1, isReady: false)` and appends it to the account's `orderHistory` (`account.appendOrder`, which also bumps `unstampedPoints` by the order's points — always 1 per order, redemption doesn't cost extra points beyond the 10 spent).
   - Presents `OrderPlacedView`; a 4-second timer flips `order.isReady`.
   - **Guard**: if `model.isApplePayEnabled == false` (App-Clip geofence failure), ordering is blocked entirely by a "Payments Disabled" alert instead.
4. **Earn reward points** — every completed order (redeemed or paid) is worth exactly **1 point**, tracked as `account.pointsEarned = orderHistory.reduce(0){ $0 + $1.points }`.
5. **Redeem** — once `unspentPoints = pointsEarned - pointsSpent >= 10`, `RedeemSmoothieButton` replaces `PaymentButton` on every smoothie's order screen; redemption is a flat **10-point cost regardless of the smoothie chosen** (no smoothie-specific point pricing).
6. **Favorites** — any smoothie can be toggled favorite from the swipe action in any list or the toolbar heart on the detail screen; purely a `Set<Smoothie.ID>` on the model, no backend, no confirmation.
7. **Recipe unlock (IAP)** — a single non-consumable StoreKit 2 product (`com.example.apple-samplecode.fruta.unlock-recipes`, $4.99 in the sample StoreKit config) unlocks the **12 of 15 smoothies that are gated behind `includingPaid`** in the Recipes tab specifically (menu/ordering is never gated). Purchase flow is `product.purchase()` (StoreKit 2 async), and ownership is re-derived at every launch via `product.currentEntitlement`, plus a long-lived `Transaction.updates` listener that reacts to refunds/family-sharing revocations by flipping `allRecipesUnlocked` back off live.

## 4. Data model

All models are plain value types (`struct`), no persistence layer beyond `UserDefaults` (one string) and StoreKit's own entitlement store — **the entire catalog, account, and order state is in-memory and resets on relaunch except**: favorites/points/orders (session-only `@Published` state on `Model`, not saved anywhere) — i.e. *nothing user-generated survives a relaunch except the Sign-in-with-Apple credential and the recipe-unlock purchase itself.* This is a demo-app simplification worth flagging explicitly for a reimplementation (a real game/product would want to persist Account).

- **`Ingredient`** (`Identifiable, Codable`): `id`, `name` (table `"Ingredients"`, localized), plus pure-presentation data — `CardTitle` (color, rotation angle, offset, `BlendMode`, opacity, font size) and two `Crop` structs (x/y offset + scale) for thumbnail vs. card art direction. **18 static ingredients** in `Ingredient.all` (avocado, almond milk, banana, blueberry, carrot, chocolate, coconut, kiwi, lemon, mango, orange, papaya, peanut butter, pineapple, raspberry, spinach, strawberry, watermelon) plus a 19th, **`water`**, deliberately excluded from `Ingredient.all` (it's a smoothie filler, never separately purchasable/orderable, and is filtered out of any "menu ingredients" display via `Smoothie.menuIngredients`).
- **`MeasuredIngredient`** (`Identifiable, Codable`): an `Ingredient` + a `Measurement<UnitVolume>`. `.measured(with: unit)` / `.scaled(by:)` fluent builders construct recipe lines (defaults to 1 unit, `.scaled` multiplies). Derives `nutritionFact`/`kilocalories` by converting its volume to mass via the ingredient's nutrition density.
- **`Smoothie`** (`Identifiable, Codable, Hashable`): `id`, `title`, `description: AttributedString` (localized markdown), `[MeasuredIngredient]`. Equality/hash by `id` only. Computed: `kilocalories` (sum of ingredient kilocalories, rounded to nearest 10), `energy` (`Measurement<UnitEnergy>`), `nutritionFact` (sum of all ingredient nutrition facts, falling back to banana's facts with a `print` warning if a smoothie somehow has no matched facts), `menuIngredients` (all measured ingredients except water), `matches(_:)` (title or any menu-ingredient name case-insensitive-contains). **15 static smoothies**, defined via a custom Swift **result-builder DSL** (`@SmoothieBuilder` for one smoothie's description+ingredients, `@SmoothieArrayBuilder` for the catalog array, supporting `if`/`if-else` conditional inclusion) — 3 always included (Berry Blue, Carrot Chops, That's Berry Bananas!) + 12 gated behind `includingPaid` for the Recipes tab.
- **`NutritionFact`** (public struct, not `Identifiable`): full USDA-style facts (saturated/mono/poly fat, cholesterol, sodium, carbs, fiber, sugar, protein, calcium, potassium, vitamin A/C, iron), each a typed `Measurement<UnitMass>`, plus a `referenceMass` and a `Density` (mass-per-volume) used to convert between "per 100g" and "per cup" representations. Supports a custom `+` operator (mass-weighted combination, used to sum a whole smoothie's ingredients) and `.converted(toMass:)`/`.converted(toVolume:)`. Loaded once at process start from a bundled `NutritionalItems.json` (18 entries, one per non-water ingredient) via a custom `Decodable` that parses "225 g" / "5 g per 1 cup"-style value strings into typed `Measurement`s — if the JSON resource is missing, silently falls back to an empty dictionary (all nutrition facts become optional-nil) rather than crashing.
- **`Order`**: `smoothie`, `points` (always 1 in practice), `isReady` (flips true after the 4s timer).
- **`Account`**: `orderHistory: [Order]`, `pointsSpent`, `unstampedPoints` (points earned since last Rewards-screen visit, drives the stamp-pop animation only — not part of the balance math), derived `pointsEarned` (sum of order points), `unspentPoints` (`pointsEarned - pointsSpent`), `canRedeemFreeSmoothie` (`unspentPoints >= 10`).
- **`Model`** (the single `ObservableObject`, environment-injected everywhere): `order: Order?`, `account: Account?`, `hasAccount` (computed — simulator always true, else requires both a stored Apple ID credential *and* a materialized `account`), `favoriteSmoothieIDs: Set<Smoothie.ID>`, `selectedSmoothieID: Smoothie.ID?` (drives cross-screen/deep-link navigation), `searchString`, `isApplePayEnabled` (App-Clip geofence flag), `allRecipesUnlocked`, `unlockAllRecipesProduct: Product?`. Persists exactly one thing across launches: the Sign-in-with-Apple user credential string, in a shared **App Group** `UserDefaults(suiteName: "group.example.fruta")` — the same suite the App Clip and widgets read/write, which is how "you signed in via the Clip" would be visible to the full app after install (in principle; StoreKit entitlements are the actual source of truth re-checked at every launch).
- No server/network layer anywhere — "ordering," "readiness," and "rewards" are all client-simulated with a fixed delay and local point math.

## 5. Localization

Fruta is explicitly Apple's WWDC21 **"Localize your SwiftUI App"** showcase, so the source leans hard on localization-aware APIs even though **this particular checkout ships only `en.lproj` and `ru.lproj`** (the real published sample normally carries ~40 locales; this repo snapshot has been trimmed to two — noted here as a fact about *this checkout*, not the design).

Localization techniques actually used in code:
- **String tables split by purpose**: `Localizable.strings` (dev-language strings auto-extracted from `Text("...", comment:)` call sites — the `en.lproj` copy is a near-empty stub since Xcode string-extraction populates it at build time), a dedicated **`Ingredients` table** for the two strings "Ingredients.menu"/"Ingredients.recipe" specifically because some languages need different words for "ingredient" depending on whether it's a shopping-list-y "recipe ingredient" vs. a descriptive "menu ingredient" (called out by an explicit code comment), and `InfoPlist.strings` for `CFBundleDisplayName`/`CFBundleName`/`NSHumanReadableCopyright` (Russian: "Фрута").
- **Pluralization via `.stringsdict`**: three format keys — `"%lld Smoothies"` (zero/one/other: "No Smoothies" / "%lld Smoothie" / "%lld Smoothies" — used by `StepperView`'s recipe batch-count label), `"%lld of 10 points earned"`, and `"You are %lld points away from a free smoothie!"` (zero case: "Congratulations, you got yourself a free smoothie!"). All follow the `NSStringPluralRuleType`/`%#@count@` stringsdict pattern.
- **Markdown-attributed localized strings**: smoothie descriptions are `AttributedString(localized:comment:)` with inline `*emphasis*` markdown, so translators can move/drop emphasis per-locale and the app renders bold spans with zero extra code.
- **`String(localized:table:comment:)`** used pervasively for data-layer strings (ingredient/smoothie names) rather than SwiftUI `Text(_:comment:)`, since those are constructed inside plain Swift model code, not view bodies.
- **Locale-aware formatting, not hand-built strings**: `Measurement.formatted(.measurement(width: .wide, usage: .food))` for calories/energy everywhere (menu rows, header, widget, nutrition facts) and `.usage: .asProvided` on the wide-header variant; `MeasurementFormatter` (`.localizedSummary(unitStyle:unitOptions:)`) for recipe quantities and nutrition-row values; **`ListFormatter.localizedString(byJoining:)`** for the natural-language ingredient list in `SmoothieRow` ("Orange, avocado, and blueberry" — conjunction/comma rules are locale-native, not hardcoded); `String.localizedCaseInsensitiveContains`/`localizedCaseInsensitiveCompare`/`localizedCapitalized`/`localizedLowercase`/`.localizedCompare` used throughout for search matching and sorting instead of ASCII string ops.
- **Preview-driven localization QA**: `NutritionFactView_Previews` explicitly renders the same view under `en`/`de`/`pt` locales side by side (`.environment(\.locale:)`) — a pattern worth adopting: locale-swept previews as a lightweight, no-device localization regression check.
- **Layout implications**: text throughout uses `.lineLimit`+`.minimumScaleFactor` (ingredient card title scales down to 25% before truncating) rather than fixed-width assumptions, anticipating string-length variance across languages.

## 6. Host-OS-only surfaces

### App Clip (`iOS/FrutaAppClip.swift`, target "Fruta iOS Clip", compiled with `APPCLIP EXTENDED_ALL`)
- **Scope exposed**: only `SmoothieMenu()` inside a bare `NavigationView` — browse + search + tap into a smoothie's detail/order flow. No Favorites/Rewards/Recipes tabs, no sidebar — reuses the exact same `SmoothieView`/`SmoothieList`/ordering code as the full app (shared target membership), it's just never given a tab/sidebar shell to reach those other sections from.
- **Invocation**: `onContinueUserActivity(NSUserActivityTypeBrowsingWeb)` parses the App Clip's launch URL — a `smoothie` query param sets `model.selectedSmoothieID` directly (deep-links straight to a smoothie's detail screen, which `SmoothieList`'s `.onChange(of: model.selectedSmoothieID)` scroll-and-select logic then honors).
- **Location-verified ordering (the "in-app twin" difference)**: if the URL also carries `latitude`/`longitude`, it builds a `CLCircularRegion` (100m radius) around that point and calls the App Clip framework's `payload.confirmAcquired(in: region)` — Apple's on-device, privacy-preserving proof that the physical device is actually near where the Clip's QR/NFC/App-Clip-Code was scanned. The completion handler sets `model.isApplePayEnabled = inRegion` on the main queue. **This is the one behavior with no full-app twin** — the full app has no equivalent geofence check; `isApplePayEnabled` defaults `true` there and is never touched. Failing the check doesn't just disable a badge — it actively blocks the buy button behind the "Payments Disabled" alert in `SmoothieView`.
- **App Store overlay**: only compiles under `APPCLIP`. `OrderPlacedView` shows a hidden `Text(verbatim: "App Store Overlay")` carrying `.appStoreOverlay(isPresented:) { SKOverlay.AppClipConfiguration(position: .bottom) }`, triggered once the Clip user has signed in (`model.hasAccount` becomes true) — nudging the Clip user to install the full app right after they've created an account, i.e. right at the moment of highest engagement.
- **Entitlements**: `iOS Clip.entitlements` declares Sign in with Apple, `associated-domains: appclips:fruta.example`, `parent-application-identifiers` back to the full app's bundle ID, and the same shared App Group as the full app (so the credential `UserDefaults` write is visible to whichever gets installed/opened next).
- **Info-Clip.plist**: `NSAppClipRequestEphemeralUserNotification` + `NSAppClipRequestLocationConfirmation` both true — declares up front that the Clip may ask for a location-confirmation prompt and may request ephemeral (Clip-scoped) push notification permission.

### Widgets (`Widgets/`, targets "Fruta iOS/macOS Widgets")
Both are `StaticConfiguration` `TimelineProvider`-based widgets sharing the full app's model *types* only (no live `Model` access — widgets construct their own static/synthetic timeline entries, no App-Group-backed live data feed is wired up despite the shared UserDefaults suite existing).
- **`FeaturedSmoothieWidget`** — families: small/medium/large/extra-large on iOS, small/medium/large on macOS. Timeline provider fabricates one entry per hour across a fixed rotation of 6 smoothies (`.atEnd` refresh policy — reload once the last entry's time passes). Layout: small = title only (scaled to fit, 1 line); medium = side-by-side title+description+calories text block and a square clipped (`ContainerRelativeShape`, matches the system widget corner radius) smoothie photo; large = same as medium's text stack but vertical, description+calories only shown at `.systemLarge`, image pinned bottom-trailing. Background is the same `BubbleBackground` used on the in-app Rewards screen. Placeholder/redacted preview state supported (`.redacted(reason: .placeholder)`).
- **`RewardsCardWidget`** — families: medium/large. Timeline is a single static entry (`points: 4`, `.never` refresh policy — this widget **never auto-refreshes**, it's illustrative/frozen). Renders the *exact same* `RewardsCard` component the in-app Rewards screen uses, in `compact` mode for medium family, over `BubbleBackground` — a literal reuse of the in-app view, not a redesigned widget-specific layout, with `hasAccount` hardcoded `true`.
- **In-app twin**: both widgets mirror real in-app screens (Menu row / Rewards card) but with **frozen, non-live data** — tapping either isn't wired to deep-link back into the app (no `.widgetURL`/`Link` present in the source read).

### Apple Pay / StoreKit
- **`PaymentButton`** wraps `PKPaymentButton` (PassKit) via `UIViewRepresentable`/`NSViewRepresentable`, styled `.buy`/`.automatic`. **Important nuance for a clean-room reimplementation**: this is only the *visual* Apple Pay button — tapping it fires a plain Swift closure (`action: () -> Void`) wired straight to `model.orderSmoothie`; there is **no `PKPaymentAuthorizationController`, no merchant session, no real payment sheet** anywhere in the source. It's a stand-in that borrows Apple Pay's button chrome for visual authenticity, not a functioning payment integration.
- **StoreKit 2** (real, functioning) powers only the recipe-unlock IAP: `Product.products(for:)` fetched at launch, `product.purchase()` (async, checked for `.success(.verified(...))`), `product.currentEntitlement` re-checked at launch to restore ownership, and an indefinite `for await update in Transaction.updates` loop that live-revokes `allRecipesUnlocked` if a transaction comes back with a `revocationReason` (refund/family-sharing revoke) and calls `transaction.finish()` otherwise. Backed by a bundled `Configuration.storekit` file (one non-consumable product, `$4.99`, localized display name/description in `en_US` and `ru`) for Simulator/local testing.

### Sign in with Apple
- `SignInWithAppleButton(.signUp, onRequest:, onCompletion: model.authorizeUser)` appears in exactly two places, both `EXTENDED_ALL`-gated: `OrderPlacedView`'s bottom banner (shown post-order if signed out) and `RewardsView`'s bottom bar (shown on the rewards screen if signed out). `Model.authorizeUser` extracts the Apple ID credential's `user` identifier, stores it in the shared App-Group `UserDefaults`, and calls `createAccount()` (only creates an `Account` if one doesn't already exist, then folds any in-flight `order` into its history). On next launch, `Model.init` re-validates the stored credential via `ASAuthorizationAppleIDProvider.getCredentialState` and silently recreates the account if still `.authorized`/`.transferred`.

## 7. Notable UI details

- **Hero/matched-geometry transitions**: the ingredient-card open/close in `SmoothieView` (§2.2) is the flagship `matchedGeometryEffect` use — single shared namespace, `isSource` flag flipped between the grid thumbnail and the overlay card depending on presentation state, asymmetric open/close spring curves, explicit z-index and accessibility choreography so hidden overlay copies never intercept touches or VoiceOver focus.
- **Custom animatable modifiers**: `AnimatableFontModifier` (tweens raw font *point size*, not just scale — used for the ingredient-card title growing/shrinking between thumbnail and card presentation) and `FlipModifier` (drives a 3D Y-axis rotation + horizontal flip via `scaleEffect(x: -1)` at the 50% rotation mark to prevent the back face from rendering mirror-reversed) — both hand-rolled `AnimatableModifier` conformances, the pre-`Animatable`-macro SwiftUI idiom for continuously interpolating custom properties.
- **`FlipView`** is reused for three unrelated flip surfaces: ingredient card front/back, order-placed "pending"/"ready" card, and (implicitly reusable) anywhere else a two-state card flip is needed — a good example of factoring a transition primitive independent of its content.
- **Materials & translucency**: `.regularMaterial` (ingredient-card scrim), `.thinMaterial` (nutrition-facts card back), `.ultraThinMaterial` (order-pending photo veil), `.bar` (bottom action bars) — all system vibrancy materials, no custom blur implementation.
- **`drawingGroup()` + procedurally-animated ambient background**: `BubbleBackground` composites ~9 `BubbleView` circles (varying size/offset/opacity) into one Metal-backed layer via `.drawingGroup()` for performance, layered under a top-to-bottom primary-color gradient in `.overlay` blend mode. Each `BubbleView` independently randomizes (`.random()`/`.random(in:)`) its own shimmer/float phase and duration at appear time, then loops two infinite `.easeInOut` animations (opacity+scale "shimmer", vertical "float") forever with per-instance random delays — animations are explicitly **skipped on macOS** (`#if !os(macOS)`), a deliberate reduced-motion-by-platform choice, not just a compile gate for API availability.
- **3D "nudge" feedback**: `StepperView`'s capsule visibly tilts (`rotation3DEffect`, ±3° depending on increment/decrement direction) then springs level again on every tap — tactile feedback with no haptic/sound involved, purely visual.
- **Card flip vs. squish button styles**: two custom `ButtonStyle`s cover almost every tappable control — `SquishableButtonStyle` (scale to 0.95 + optional opacity fade while pressed; used for ingredient thumbnails, card action buttons, redeem button) and `CapsuleButtonStyle` (capsule background + `.hoverEffect(.lift)` on iOS/iPadOS for trackpad/Pencil hover — used for the sidebar Rewards "Pocket" button and sheet dismiss buttons) and `PurchaseButtonStyle` (high-contrast black/white pill, explicitly color-scheme-aware rather than using semantic colors, for the recipe-unlock buy button).
- **Custom `ToggleStyle`**: `CircleToggleStyle` swaps the native switch for a plain checkmark-circle/circle SF Symbol pair — used for the recipe-ingredient "gathered" checklist toggle — with explicit "Checked"/"Unchecked" accessibility labels since the visual no longer resembles a standard switch.
- **Custom unit iconography**: `Unit.unitIcon` extension protocol (`UnitIconProvider`) lets `UnitMass` return a system `scalemass.fill` glyph while `UnitVolume` returns either a **custom SF-Symbol-style vector asset** (`cup`/`qt`/`tbsp`/`tsp`/`gal` — real custom symbol sets shipped in `NutritionFactsAssets.xcassets`) or a system `drop.fill` fallback for any other unit — a small but complete "iconography as data" pattern mirroring the ingredient `CardTitle`/`Crop` art-direction tables.
- **Accessibility patterns used consistently, not just spot-fixed**: `.accessibilityElement(children: .combine)` on composite rows/headers so VoiceOver reads them as one phrase; `.accessibilityElement(children: .contain)` on card-like containers so internal buttons stay individually reachable; explicit `.accessibility(label:)` overrides anywhere an icon+text `Label` or truncated text could mislead VoiceOver; `.accessibility(sortPriority:)` + `.accessibility(hidden:)` choreography around the ingredient-card overlay stack; two custom `accessibilityRotor`s per list screen (all items / favorites-only); `accessibilityRepresentation` substituting a native `Stepper` for the custom tilting `StepperView`; `.dynamicTypeSize(.large)` floor on the capsule button style. `.hoverEffect(.lift)` for iPadOS pointer/trackpad support on capsule buttons.
- **Cross-platform value bridging**: `Color(uiColor:)` / `Color(nsColor:)` used where a platform system color has no direct SwiftUI semantic equivalent (e.g. `RecipeView`'s background), gated by `#if os(iOS)`/`#if os(macOS)` throughout rather than a shared abstraction layer — the codebase's general strategy for iOS/macOS divergence is small inline `#if os()` branches at the point of difference (corner radius values, control heights, frame sizing, hover effects) rather than platform-specific view files.
