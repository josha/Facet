# Guide candidate release and comparison

Registered on 2026-10-26 before the next complete paired author run.
This plan follows the compact-collection and Trail Outfitters diagnostics.
It does not replace their frozen inputs or results, or the original benchmark.

## What the current evidence supports

The new guide transfers useful compact collection structure to another game.
The fresh Sol 6.1 Medium author showed three complete records in landscape.
The collection example also passed targeted native short-height checks at
Largest text. These are useful design and behavior observations, not complete
acceptance or a visual win over Plain. Full author usage was unavailable.

The navigation reversal exposed both a framework edge case and a missing
ownership explanation. The framework fix must land separately. The guide must
still teach retained path entries: replacement must animate correctly, but it
does not preserve state belonging to an old page instance.

## Check-in gate

Prepare a clean candidate PR from current main, with these changes only:

- The skill, its conditional references, reusable examples and exact API docs.
- The example typecheck project and necessary documentation regression tests.
- A short evidence record with hashes, commands, native receipts and limitations.

Exclude generated places, frozen submissions, experiment games, unrelated
runtime fixes and retrieval-tool changes. Review the large working diff by
dependency, rather than committing the experiment worktree as a unit. Confirm
that every referenced capability and file exists in the candidate checkout.
Old guide files may remain for history, but active routes must have one answer.

Validate exact candidate bytes: documentation budgets and links, strict example
types, required repository checks, and representative native tasks. Close the
known collection gaps through real input: search and empty recovery, filter and
reset, detail and Back, rejected then accepted server action, retained draft and
scroll state, controller entry/return, Largest text, and open orientation change.
Test the navigation fix with the original replacement trigger as well as normal
push/pop. A passing targeted case does not complete another acceptance row.

Check in as a tested guide candidate when these checks pass. Do not label it
superior to Plain or claim that every possible composition is verified.
Catalog coverage and successful use are separate measures.

## Freeze the next comparison

Keep the original full game brief, acceptance rows, author tools, Sol 6.1 Medium
and 1800-second author deadline. Hash the prompt, source kit, skill, docs and
runtime. Authors get no previous submission, evaluation code or design coaching.

Use three arms:

- P: the original Plain instructions.
- F0: the original guide with the same corrected Facet runtime used by F1.
- F1: the candidate guide with that identical corrected runtime and lookup tools.

This isolates the guide effect. It is not a docs-only comparison against the
old a79dae64 runtime: radial and navigation fixes are explicit shared factors.
Keep the original paired run as a separate historical baseline. Test retrieval
changes in a later arm, not hidden inside F1.

Before paid author work, prove scoped Studio ownership, repeatable Play/Stop,
phone and controller input, valid UI captures, deadline termination, and public
runner token usage including cached input. Use the existing Verify runner and
reports. Do not infer usage from private account/session logs or document words.
If admission fails, repair the evaluator; do not charge the failure to Facet.

Start with one complete P/F1 pair as pipeline calibration. Retain and report it,
but exclude it from the confirmatory score. It should expose a broken full task
or measurement path before another batch. Then freeze unchanged bytes and run
three independent blocks of P/F0/F1 with balanced order. Run serially or keep
resource contention equal. Seed labels identify independent runs, not a promise
of deterministic model sampling. Any candidate revision starts a new batch.

## Judgment and measures

Freeze submissions before evaluation and reopen copies. Check every acceptance
row, including real gameplay and repeat transactions. Separate authored bugs,
library defects, documentation friction and evaluator failures. Never substitute
a repaired submission or combine the successful parts of multiple authors.

Validate matched captures before judging. Reject stale, world-only, wrong-state,
wrong-window and wrong-device images. Use anonymous identifiers and both orderings
with a fixed judge model and effort. Score hierarchy, game identity, useful art
scale, sensible interaction, readable information and composition for the task.
Judge desktop, portrait and short-height landscape separately. Equal-weight the
predeclared states within each form, then the forms within each seed. A win is 1,
a tie 0.5 and a loss 0. Report per-seed scores and order disagreement; reversed
orders and multiple screens are not independent author samples.

Record total tokens including cache, cached input, uncached input and output;
direct docs response volume and repeated reads; author wall time and repair loops.
Keep setup, evaluation and judging clocks and usage separate. Compare total-token
ratios per pair and across the batch. No missing usage may count as zero.

Measure native frame distributions and retained memory serially on the same
machine, foreground state, viewport, graphics settings and scene workload.
Warm up, alternate arm order, and measure after at least 20 successful task and
return cycles. Preserve raw samples. An unsuccessful return cannot create a
favorable retention measurement. Report noise and uncertainty near a threshold.

## Decision rules

Stop for invalid custody, capture/input or usage, or a critical treatment-induced
gameplay/access regression. Preserve every run and its reason. Fix the cause and
start a newly labeled batch; do not quietly replace unfavorable runs.

Advance from the three-block pilot only if F1 has complete required evidence,
no critical behavior/access regression, at least 70% visual preference against
P overall, no device form below 50%, and better preference than F0. Both the
aggregate total-token ratio and median paired ratio F1/P must be at most 1.30.
Require less than 5% regression in native frame timing and retained memory.
Report author time without inventing a new speed target.

Confirm the selected candidate with six new paired P/F1 blocks using those same
criteria. Report paired effects and uncertainty clustered by author seed; a
borderline or inconclusive result supports a narrower claim, not a general win.
The user's present target is comparable-or-better UI with at most 30% more total
tokens. This does not satisfy or replace the historical benchmark's stronger
50%-of-Plain token and 60%-of-Plain time efficiency claim. Report that claim only
if its unchanged original criteria also pass.
